# قرار إعادة كتابة Onboard من الصفر

## القرار

ستُعاد كتابة المنتج باسم **Onboard Next** باستخدام **Rust 2021** للنواة وكل منطق التطبيق. لا يقتصر القرار على استبدال لغة Python: بل يفصل مجال لوحة المفاتيح عن الواجهة وعن واجهات أنظمة التشغيل، بحيث تبقى القواعد والاختبارات واللغات مشتركة بينما تكون كتابة النص وإدارة النافذة والتوقيع والتغليف مسؤوليات منصة محددة.

> لا توجد لغة تجعل إدخال النص بين التطبيقات متطابقاً تلقائياً. القوة هنا تأتي من Rust للنواة الآمنة، ومن جسور Windows وmacOS وLinux الضيقة التي تعلن قدرتها وحدود صلاحيتها صراحةً.

| الطبقة | التقنية | المسؤولية |
| --- | --- | --- |
| `onboard-domain` | Rust بلا واجهة ولا FFI | حالة التخطيط، مفاتيح اللوحة، الحافظة، موضع النافذة، الاختصارات، وسياسة الخصوصية. |
| `onboard-i18n` | Rust + Fluent (`.ftl`) | اختيار اللغة، صيغ الجمع، رسائل الأخطاء، اتجاه RTL، واختبارات pseudo-locale. |
| `onboard-input-api` | Rust trait | عقد موحّد لحقن Unicode والمفاتيح وتبديل مصدر الإدخال وإبلاغ القدرات. |
| `onboard-platform-windows` | Rust + Win32/TSF | `SendInput` لـUTF-16، TSF عند اكتماله، tray، startup، نافذة غير ناشطة، والتحقق من UIPI. |
| `onboard-platform-macos` | Rust + Quartz | `CGEvent`، أذونات Accessibility، tray، وتوقيع/Notarization. |
| `onboard-platform-linux` | Rust + X11/Wayland adapters | تكامل سطح المكتب، قيود Wayland، ومدير الإدخال المناسب للتوزيعة. |
| `onboard-ui-egui` | Rust + `eframe`/`egui` | لوحة مدمجة مشتركة، رسم المفاتيح، الخطوط المضمّنة، الحافظة، الإيموجي، وحفظ الموضع. |
| `onboard-ui-gtk` | `gtk4-rs`، اختياري | واجهة Linux متعمقة عند الحاجة إلى تكامل GNOME أعلى من الواجهة المشتركة. |
| `onboard-app` | Rust | تركيب المكونات، دورة حياة العملية الواحدة، الإعدادات، والتشخيص. |

## لماذا Rust

Rust مناسب للنواة لأنها تتعامل مع حالة طويلة العمر، رسائل متزامنة بين الواجهة وSystem Tray، وFFI حساس مع Windows وmacOS. يفرض النظام النوعي وتملك الذاكرة حداً واضحاً بين الحالة المشتركة وواجهات النظام غير الآمنة. توضع كل كتلة `unsafe` داخل bridge صغير ومختبر بدلاً من نشرها داخل التطبيق.

لا يُختار C++ رغم قوته، لأن عبء إدارة الذاكرة والتزامن أكبر في تطبيق يستمر في الخلفية ويتعامل مع نافذة وtray وأحداث نظام متعددة. ولا يُختار Python أو JavaScript للنواة، لأنهما لا يقدمان نفس الحزمة المتجانسة من الأداء وتوزيع binary والجسور منخفضة المستوى. يمكن الاحتفاظ بـGTK4 عبر `gtk4-rs` عندما يكون التكامل العميق مع Linux أهم من توحيد الواجهة.

## الواجهة واللغات

الواجهة الافتراضية ستكون `eframe`/`egui` لأنها تسمح ببناء نافذة أصلية وحفظ حالتها وضبط الخطوط المضمّنة من Rust. تُضمّن خطوط لكل النصوص غير اللاتينية المطلوبة، ولا يعتمد عرض العربية أو الإيموجي على خط نظام المستخدم.

تنتقل النصوص الجديدة إلى Fluent في مجلد `locales/<language>/onboard.ftl`. يتكون كل معرف من مفتاح ثابت ودلالة واضحة، وتخضع العربية لاختبار اكتمال وRTL. تبقى ملفات gettext الحالية في مرحلة التوافق فقط إلى أن تنتقل الشاشة المقابلة؛ لا يحوّل المشروع تلقائياً عشرات الترجمات البشرية الجزئية إلى ترجمات مُختلقة.

## عقد الإدخال متعدد المنصات

```text
Keyboard UI → domain action → input-api capability check → platform bridge → system input API
```

يعرّف العقد عمليات `inject_text(UTF-8)` و`inject_key` و`switch_input_source` و`capabilities`. يحوّل كل bridge النص إلى تمثيل النظام الصحيح ويعيد سبب فشل واضحاً. على Windows، يظل تطبيق أعلى امتيازاً خارج نطاق حقن عملية أقل امتيازاً؛ لذلك تعرض الواجهة حالة صريحة بدلاً من الادعاء بنجاح غير حاصل. على macOS، لا تُفعّل الكتابة حتى تمنح أذونات Accessibility.

## مسار الترحيل

| المرحلة | الناتج القابل للإصدار | معيار الخروج |
| --- | --- | --- |
| R0 | مساحة Rust ونواة domain وواجهة input-api | اختبارات مستقلة بلا GTK/Python. |
| R1 | لوحة Windows قابلة للكتابة بالعربية والإنجليزية مع tray وsingle-instance | اختبار تفاعلي على Windows x64 وARM64. |
| R2 | macOS مع CGEvent وأذونات Accessibility | توقيع وتجربة مستخدم على macOS x64 وARM64. |
| R3 | Linux: X11 ثم Wayland وفق القيود الموثقة | حزم Debian/RPM/Arch/Flatpak واختبارات تشغيل. |
| R4 | Fluent وRTL كاملان وترحيل جميع الشاشات | تقارير اكتمال لكل لغة واختبارات pseudo-locale. |
| R5 | قناة مستقرة موقعة وتحديث آمن | Authenticode وcodesign/notarization والتحقق قبل التثبيت. |

## ما يُحتفظ به وما يُستبدل

تُحتفظ فقط بالمعرفة الوظيفية: التخطيطات، رسائل الترجمة، اختبارات سلوك الإدخال، ووصفات التوزيع الناجحة. تُستبدل واجهة Python/GTK3 القديمة، منطق تشغيلها، وترابطها الداخلي تدريجياً. تبقى شجرة التطبيق القديم قابلة للبناء إلى أن تتجاوز النواة الجديدة كل معيار تشغيل؛ لا يحدث حذف واسع قبل تحقق البديل على أنظمة فعلية.
